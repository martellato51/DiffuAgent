1. v1 선행 실험

v1은 v2 이전에 수행한 선행 진단 실험이다. LLaDA가 BFCL function schema를 보고 gold trajectory의 hop-level action intent를 얼마나 복구할 수 있는지 확인하는 것이 목적이었다. BFCL v3 multi_turn_base 50개 sample의 모든 user turn을 이어 붙여 하나의 full goal로 만들고, 모델은 전체 multi-turn goal을 한 번에 본다 (offline full-trajectory planning).

예를 들어 multi-turn sample에 세 개 user turn이 있으면 v1 prompt의 goal은 다음처럼 구성된다. 모델은 이 전체 goal을 한 번에 보고 [A1], [A2], ... 형태의 full trajectory action plan을 생성한다.

[turn 1] Move log.txt into the archive folder.

[turn 2] Search the archived log for lines containing "Error".

[turn 3] Show me the last 20 lines of the archived log.

v1 실험 설정
항목설정

입력모든 user turn을 이어 붙인 full goal (offline full-trajectory planning)

1.1 v1 프롬프트 설계

v1의 exact_name_a mode는 다음과 같은 action-only format을 요구했다.

[A1] Use <exact_function_name>: <intended action>. Inputs: <entities, arguments, or result-dependent inputs>.
[A2] Use <exact_function_name>: <intended action>. Inputs: <entities, arguments, or result-dependent inputs>.

중요한 prompt rule은 다음이다.

- Use the exact function name from the available function schema.
- Each [A] must describe exactly one intended function/tool action.
- Do not output executable BFCL function-call syntax.
- Do not output JSON as the final answer format.
- Do not write thoughts, observations, or final summaries.
- Include known file names, ids, dates, locations, entities, and literal values when stated.
- If an input depends on an earlier result, describe that input naturally instead of guessing the concrete value.
- Use only the available functions.
- Include only actions needed to satisfy the user request.

Inputs:는 executable JSON argument를 요구하는 필드가 아니다. 목적은 known literal과 prior-result-dependent input을 judge가 구분할 수 있게 하는 것이다. 예를 들어 order id가 이전 place_order 결과에서 나와야 한다면, {"order_id": 1}처럼 concrete value를 invent하지 말고 order_id from previous result처럼 unresolved input으로 남기도록 했다.

이 설계는 v2의 $id reference 또는 flat placeholder 설계로 이어진다. v1에서는 unresolved dependency를 자연어로 남겼고, v2에서는 이를 더 구조화된 output syntax 안에서 보려고 했다.

1.4 v1에서 v2로 넘어간 이유

v1의 결과는 LLaDA가 BFCL function schema를 보고 tool-use action surface를 만들 수 있음을 보여줬다. 하지만 그 출력만으로는 실패 원인을 충분히 분해하기 어려웠다. Natural-language [A] unit은 action intent judge에는 적합했지만, executable schema, current-turn dependency, state visibility, denoising trace를 정밀하게 분석하기에는 부족했다.

v1에서 남은 문제v2 대응
full-trajectory planning — turn별 current planning 불가episode 유지, current turn마다 별도 generation
[A] 자연어 unit — schema validity 직접 확인 어려움numbered tool_name(param=value) plan grammar
prior-result input을 자연어로만 표현explicit $id reference 또는 flat placeholder
hidden path/id — static matching 불공정deterministic state_view=tree 제공
all-pairs LLM judge 의존도 높음P0 deterministic matcher + P1 selective judge
dependency/parallelism을 output에서 직접 보기 어려움explicit DAG condition과 flat condition 비교
confidence가 dependency 구조와 연결 약함response span, $id dependency, commit step 함께 분석

또 다른 중요한 동기는 prompt 구조 자체에 있었다. v1의 자연어 [A] plan에서는 어떤 action이 다른 action의 결과를 필요로 하는지 reference를 안정적으로 찾기 어려웠다. 후처리로 gold DAG와 연결하려 해도, generated plan 내부의 dependency 후보가 명시적으로 남지 않는다.

Goal이 user query를 단순히 concat한 점, 최종적으로 보고자 하는 denoising dynamics와 subtask들의 denoising 패턴간의 관계를 보지 못하는 점, 실험설계에 레퍼런스를 찾기 힘들다는 점을 바탕으로 v2 실험을 진행하였다.

2. v2 실험 목적

think_parallel_v2는 BFCL v3 multi_turn_base에서 DLM/LLaDA가 현재 user turn에 필요한 tool-use plan을 LLMCompiler-style grammar로 생성하면서, 병렬 가능한 action과 이전 action 결과가 필요한 action을 구분할 수 있는지를 보기 위한 실험이다.

Q1. LLaDA가 exact BFCL answer wrapper 없이도 current turn에 필요한 tool action node를 복구할 수 있는가?

Q2. 생성된 numbered plan과 denoising trace 안에서 gold DAG의 병렬/순차 구조와 연결될 수 있는 signal이 보이는가?

v1은 [A1] Use ... 형태의 natural-language action unit을 만들고 post-hoc judge로 gold hop과 맞췄다. v2는 한 단계 더 직접적으로 LLMCompiler-style plan grammar를 사용한다.

v1 출력 형식

[A1] Use tool_name: natural-language action.
     Inputs: known literal or unresolved input.

자연어 unit. dependency는 "prior result"처럼 서술.

v2 출력 형식

Thought: <optional one-line strategy>
1. tool_name(param=value)
2. tool_name(param=$1.field)
<END_PLAN>

LLMCompiler-style numbered plan. dependency는 $id로 명시.

v2의 explicit condition은 LLMCompiler가 실행 전에 plan DAG를 먼저 만드는 방식에서 아이디어를 가져왔다. 다만 여기서는 일반 LLM agent가 아니라 DLM/LLaDA가 numbered plan을 생성하게 하고, 그 안에서 $id reference를 통해 "이 action은 앞 action 결과가 필요하다"는 구조를 직접 남기도록 했다. 즉 v2의 explicit condition은 LLMCompiler-style 사전 DAG planning 단계를 DLM generation에 적용한 진단 설정이다.

따라서 v2는 v1보다 높은 점수를 만들기 위한 실험이라기보다, v1에서 하나로 뭉쳐 보이던 실패를 tool validity, schema validity, action recovery, dependency recovery, denoising signal로 나누어 보기 위한 후속 실험이다.

이번 state-view rerun에서 비교한 조건은 두 가지다.

conditionmode역할
smoke_explicit_state_tree llmcompiler_explicit_dag deterministic state view 위에서 current-plan 결과가 필요한 argument를 $id 또는 $id.field로 표현하는 explicit DAG condition.
smoke_flat_state_tree llmcompiler_flat_plan deterministic state view 위에서 numbered action reference를 argument 안에 쓰지 않는 flat plan condition. result-dependent argument는 angle-bracket placeholder로 둔다.

두 조건의 비교 의도는 단순하다. 같은 state view 위에서 $id reference를 직접 허용할 때와 금지할 때, action recovery와 dependency/denoising signal이 어떻게 달라지는지를 본다.

3. v2 실험 설계

3.1 Episode 유지 + turn별 생성

BFCL multi_turn_base record는 여러 user turn을 포함한다. v2는 turn을 독립 sample로 완전히 떼어내지 않고 full episode를 유지한다. 다만 모델 호출은 current turn마다 한 번씩 수행한다.

selected episode:
  turn 1 → one model generation
  turn 2 → one model generation with turn 1 previous context
  turn 3 → one model generation with turn 1-2 previous context

즉 episode 하나를 한 번의 model call로 처리하는 것이 아니라, episode 안의 각 user turn마다 별도의 generation을 수행한다. 20 episodes가 70 turns를 포함하면 condition 하나당 70번의 model generation이 발생한다.

3.2 Previous context는 oracle context다

현재 turn 이전의 user request, gold call, gold observation은 prompt에 포함된다. 현재 turn의 gold call은 포함되지 않는다. 이전 turn context는 model-generated previous plan이 아니라 gold previous plan이다.

Prompt 구조 (Previous Context)

Completed Previous Turns (read-only context):
Their Observations may be used as concrete input values.
Do not output Observation lines in the Current Plan.

Turn 1 User: ...
Previous Plan:
1. previous_gold_call(...)
Observation: ...
<END_PLAN>

Current Environment State:
...

Current Turn User: ...

Current Plan:
이 설계의 목적: previous-turn error accumulation을 제거하고, current-turn plan 생성 능력을 분리해서 보기 위한 것이다. 모델이 이전 turn을 잘못 생성했을 때 그 오류가 다음 turn 평가에 누적되는 confound를 없앤다. oracle context 덕분에 current turn의 state-dependent input은 gold observation에서 concrete value로 가져올 수 있다.

3.3 Smoke Episode Selection

Episode 필터 기준
episode_filter = intra_turn_parallel:
  has graph annotation
  turn_bound_max_width >= 2       ← 같은 turn 안에 병렬 가능 action 존재
  n_intra_turn_antichain_pairs > 0

overlap set = v1 50-sample ∩ v2 intra-turn-parallel 73-episode
→ smoke 기본 set: 20 episodes · 70 turns · 142 gold hops

전체 BFCL 대표 표본이 아니라 v1-v2 비교 가능성과 intra-turn parallel structure를 동시에 만족하는 diagnostic comparison set이다.

3.4 Current Environment State View

user query만 보고는 숨겨진 파일 경로나 내부 id를 알 수 없는 case가 있다. 이를 해결하기 위해 current turn 직전의 environment state를 deterministic text로 prompt에 제공한다.

State View 생성 방식

  • BFCL initial_config에서 시작
  • 이전 turn의 gold call만 replay
  • rule-based renderer로 text 생성
  • current turn gold call은 사용하지 않음
  • LLM summary 아님 — 완전히 deterministic

State View 설정

include_file_content: false
max_depth: 6
max_entries: 200
max_chars: 6000
실제 최대 길이: 2,872 chars
진단 설정임에 유의: state_view=tree는 official BFCL interactive inference와 다르다. 실행 전에 현재 상태를 text로 보여주고 plan을 한 번에 생성하게 한다. API domain에서는 access_token, card_number 같은 synthetic key가 prompt에 포함될 수 있다. 결과는 "모델이 실제 BFCL에서 이렇게 행동한다"가 아니라, "현재 상태가 보이는 조건에서도 plan recovery가 되는가"로 해석해야 한다.

3.5 Generation 설정

파라미터값이유
gen_length128numbered plan이 대부분 128 token 이내에 수렴
steps128충분한 denoising iteration
block_length128output 전체를 단일 block에서 denoising — block boundary confound 제거
block_length=128을 선택한 이유: block_length=32처럼 output을 여러 block으로 나누면 앞 block action이 먼저 확정되고 뒤 block이 맞춰지는 형태가 된다. 그러면 $id reference나 commit pattern이 모델의 dependency planning 때문인지 block-wise generation artifact 때문인지 해석이 어려워진다. 하나의 block에서 전체를 denoise하면 action들이 더 동시에 조정될 수 있어, dependency/commit-step 분석에서 confound가 줄어든다.

3.6 Confidence Trace 구조

v2는 v1의 traceable LLaDA backend를 재사용한다. generated output 영역을 mask token으로 채운 뒤 block 단위로 denoising하고, token이 commit될 때 trace row를 남긴다.

field의미
blockgenerated output을 block_length 단위로 나눈 block index
commit_step전체 denoising loop 기준 token이 확정된 step
step_in_block해당 block 내부 step
positiongenerated output token position
token_text확정된 token의 decoded text
confidencesoftmax(logits)[selected_token] — commit 순간 선택 확률
char_start, char_enddecoded response 안 character span

저장되는 것은 committed token row만이다. same position의 per-step history, commit 전 top-k 후보 변화, uncommitted masked position의 confidence는 직접 관측하지 않는다.

4. Matcher와 평가 방식

4.1 P0 Deterministic Matcher

generated numbered action unit을 current-turn gold hop에 연결한다. 목적은 generated action이 어떤 gold hop에 붙는지 확인하고, generated $id edge가 gold DAG edge 또는 gold antichain 구조와 어떻게 맞는지 보는 것이다.

P0 Matching Rule

1current-turn graph_stats.gold_hop_ids만 candidate로 사용
2exact normalized tool name match를 강한 anchor로 사용
3argument token / parameter overlap은 tie-breaker와 보조 score로 활용
4$1.result, <placeholder>는 unresolved input으로 기록하고, literal mismatch만으로 즉시 실패시키지 않음
5score threshold 미만 unit은 unmatched로 남김

P0는 final correctness judge가 아니다. schema는 틀렸지만 의미가 맞는 action, boolean 값이 반대인 action, semantic synonym, decomposition mismatch 같은 경우는 deterministic rule만으로 안정적으로 판정하기 어렵다.

4.2 P1 Selective LLM-as-Judge

P0가 판단하기 어려운 high-impact pair만 LLM-as-judge에 보낸다. 모든 pair를 judge하지 않는다.

P1 대상 조건

  • P0 match_strength=wrong이지만 best_candidate_score가 높은 pair
  • P0 partial이지만 schema-invalid인 pair
  • P0 exact/partial이지만 boolean, mode, numeric argument conflict가 의심되는 pair
  • invalid/synonym tool이지만 semantic candidate가 있는 pair
  • generated dependency edge endpoint가 unmatched인데 semantic match 가능성이 있는 pair
  • current turn의 Q2 dependency 분석에 직접 영향을 주는 pair

4.3 Hybrid Resolver

P0 결과를 기본값으로 두고, P1 judge 결과가 있는 pair만 보정한다.

보정 유형설명
semantic rescueP0 wrong → judge semantic/partial/exact
conflict downgradeP0 exact/partial → judge wrong (input conflict)
schema rescueschema-invalid이지만 judge가 action/input compatible 판정
duplicate clarificationrepeated unit vs distinct coverage 구분

같은 gold hop에 여러 generated unit이 붙으면 가장 좋은 unit만 recall numerator에 세고 나머지는 duplicate로 표시. duplicate row는 over-generation/repeated action failure 분석에 사용한다.

4.4 평가 지표 해석

5. v2 프롬프트: explicit vs flat

공통 생성 contract

Given the current user turn, create the minimal sufficient tool-use plan.
1. 먼저 current turn 해결에 필요한 최소 action set 선택
2. 그 안에서 병렬성 최대화 (불필요한 helper action 추가 금지)

공통 rule:
- Output only Thought, numbered actions, and <END_PLAN>
- Each action must use exact schema parameter names
- IDs start at 1 and strictly increase within the Current Plan
- Do not repeat previous-turn actions unless explicitly asked
- Do not add helper actions unless their outputs are needed
- Do not call join()

smoke_explicit_state_tree

state_view=tree + llmcompiler_explicit_dag. 현재 plan 안에서 이전 action 결과가 필요하면 $id 또는 $id.field를 사용. previous turn plan id를 참조하면 안 된다. previous turn 필요 값은 Observation text에서 concrete value로 가져온다.

Thought: <optional>
1. get_zipcode(city="San Francisco")
2. get_zipcode(city="Rivermist")
3. estimate_distance(
     cityA=$1.zipcode,
     cityB=$2.zipcode)
<END_PLAN>

1, 2는 독립 → 병렬 가능. 3은 1, 2 결과가 필요 → $id 참조.

smoke_flat_state_tree

state_view=tree + llmcompiler_flat_plan. argument 안에 numbered reference 금지. result-dependent argument는 angle-bracket placeholder. $1 등이 나오면 flat_reference_violation_count에 기록.

Thought: <optional>
1. get_zipcode(city="San Francisco")
2. get_zipcode(city="Rivermist")
3. estimate_distance(
     cityA="<zipcode for SF>",
     cityB="<zipcode for Rivermist>")
<END_PLAN>

$id 없이 token confidence/commit-step만으로 dependency signal 포착 가능한지 확인.

두 조건의 비교 의도: 같은 state view 위에서 $id reference를 허용할 때와 금지할 때, action recovery와 dependency/denoising signal이 어떻게 달라지는지를 본다.

6. v2 실험 결과

6.1 Run Coverage

두 condition 모두 format_parse_rate=1.0, P1 judge error 0. explicit이 flat보다 19개 더 많은 unit 생성 및 over-generation 더 많음.

6.2 Format Sanity

Format sanity는 plan이 정답인지가 아니라, 모델 출력이 약속한 LLMCompiler-style surface로 읽히는지를 본다. parse rate는 generation 중 parser가 action line을 구조화한 비율이고, parse errors는 invalid tool name, 잘못된 reference, malformed line 같은 형식 문제다. zero-unit turns는 parser가 action을 하나도 찾지 못한 turn, duplicate actions는 같은 raw action이 반복된 경우다.

conditionparse ratemissing END_PLANparse errorszero-unit turnsduplicate actions
explicit 1.000017310 turns / 13 dup.
flat 1.00002472 turns / 3 dup.

parse error 대부분은 invalid tool name. explicit은 invalid tool-name 16건 + non-preceding $1 reference 1건. flat은 invalid tool-name 23건 + $10000를 reference로 읽은 1건.

6.3 Tool/Action Coverage

Tool/action coverage는 correctness 이전의 surface-level 지표다. valid tool rate는 generated action의 tool name이 prompt에 제공된 function list 안에 있는 비율이고, gold와 맞는다는 뜻은 아니다. over-gen, under-gen, equal은 turn별 generated action 수를 current-turn gold action 수와 비교한 count다.

conditionvalid tool rateover-gen turnsunder-gen turnsequal turns
explicit 84.6% (126/149) 27 / 7021 / 7022 / 70
flat 76.2% (99/130) 20 / 7025 / 7025 / 70

flat이 compact하다는 사실과 action recovery가 좋다는 사실은 분리해서 봐야 한다.

6.4 Schema Validity

Schema validity는 generated action이 제공된 tool의 parameter schema를 지켰는지 보는 지표다. schema-valid는 required parameter가 있고 unknown parameter가 없는 action 비율이며, gold action과 의미가 맞는지는 별도 matching에서 판단한다. 따라서 schema-valid action도 wrong일 수 있고, schema-invalid action도 P1에서 intent만 partial로 rescue될 수 있다.

conditionschema-valid rateschema-invalid주요 오류
explicit 54.4% (81/149) 68/149 param= wrapper, wrong param name, missing required field
flat 51.5% (67/130) 63/130 arg= wrapper, JSON-like malformed call, wrong param name
두 condition 모두 schema-valid rate 50% 내외. lockDoors(param={...}), get_zipcode(arg={...}) 같은 wrapper 오류가 반복된다. P1은 schema surface error 중 일부를 partial로 rescue할 수 있지만 executable correctness로 간주해선 안 된다.

6.5 P0 / P1 Action Matching

Action matching은 generated unit을 current-turn gold hop에 붙이는 단계다. gold recall 계열은 gold hop을 denominator로 하며, duplicate를 제거한 뒤 얼마나 많은 gold hop이 covered 됐는지 본다. unit rate는 generated unit을 denominator로 하며, 생성된 action 중 몇 개가 어떤 gold hop에 붙었는지 보는 precision-like 지표다.

P0 Deterministic Matcher

P0는 exact tool name, argument overlap, schema diagnostics를 이용한 deterministic matcher다. 빠른 1차 anchor를 제공하지만 final correctness judge는 아니다.

conditiongold recallstrict single recallunit rateexactpartialwrong
explicit 0.4010.2110.383302792
flat 0.3730.2540.408361777

P1 Hybrid Matcher (최종)

P1 hybrid는 P0 결과를 기본값으로 두고, ambiguous/high-impact pair만 LLM-as-judge로 보정한 최종 action recovery 지표다. hybrid strict single은 exact behavior, compatible 또는 unresolved-ok input, single-hop match를 모두 만족한 가장 보수적인 recall이다.

conditionhybrid gold recallhybrid strict singlehybrid unit rateexactsemanticpartial
explicit 0.366 0.169 0.396 26330
flat 0.359 0.197 0.415 28917

이 표에서 hybrid gold recall과 hybrid strict single의 denominator는 142개 current-turn gold hop이고, hybrid unit rate의 denominator는 generated action unit 수다. 따라서 explicit은 hybrid gold recall 0.366 ≈ 52/142, hybrid strict single 0.169 ≈ 24/142, hybrid unit rate 0.396 = (26 exact + 3 semantic + 30 partial) / 149로 읽는다. flat은 hybrid gold recall 0.359 ≈ 51/142, hybrid strict single 0.197 ≈ 28/142, hybrid unit rate 0.415 = (28 exact + 9 semantic + 17 partial) / 130이다.

핵심: hybrid matched gold recall이 거의 같다 (explicit 0.366 vs flat 0.359, 차이 0.007). $id grammar를 허용한 explicit이 action recovery에서 flat을 뚜렷이 이겼다고 말하기 어렵다. 오히려 strict single recall은 flat이 더 높다 (0.197 vs 0.169).

P1 개입 패턴

P1 개입 패턴은 LLM judge가 P0를 어떻게 보정했는지 보여준다. semantic rescue는 P0가 wrong으로 본 pair를 judge가 semantic/partial/exact로 살린 비율이고, conflict downgrade는 P0 matched pair를 judge가 argument conflict 등으로 wrong 처리한 비율이다. schema surface error는 schema 표면은 틀렸지만 intent는 맞을 수 있는 경우를 뜻한다.

conditionjudged pairssemantic rescueconflict downgradeschema surface error
explicit 6119.7%16.4%34.4%
flat 5221.2%19.2%28.8%

P1은 score 향상 단계가 아니다. 두 condition 모두 P0 false positive를 downgrade했다.

6.6 Dependency / Reference Behavior

Dependency/reference 지표는 generated plan 안의 $id reference를 parser가 dependency edge로 잡은 뒤, 그 edge를 hybrid-matched gold hop으로 lift해서 gold DAG와 비교한 것이다. 여기서 dep. edges는 generated $id 기반 edge 수이고, gold dependency action 수가 아니다. unmatched endpoint가 많으면 edge의 source/target action이 gold hop에 안정적으로 붙지 않아 DAG 비교 자체가 어렵다는 뜻이다.

explicit은 $id reference를 8개 생성했지만 gold dependency로 안정적으로 align된 edge는 없다.

explicit generated edge alignment:
  unmatched_both_endpoints = 3
  unmatched_source         = 1
  unmatched_target         = 3
  same_gold_hop            = 1
gold dependency check 59개 중 대부분은 generated endpoint가 gold hop에 매칭되지 않아 구조 비교 자체가 불가능했다. 현재 결과만으로는 LLaDA가 gold DAG dependency를 복구한다고 말할 수 없다.

계산은 plan_units.jsonl의 response_spans.function_name과 token_confidence.jsonl의 token character span을 overlap시켜 수행했다. 각 action unit마다 function-name token들의 confidence와 commit_step 평균을 먼저 구하고, 그 unit-level 값을 root/dependency group별로 다시 평균했다. 따라서 긴 function name이 토큰 수 때문에 과도하게 가중되지 않는다.

Trace-level signal 존재: explicit condition에서 dependency action은 root action보다 action span 기준 평균 ~15.7 step 늦게 commit되고, action confidence도 0.128 낮다. function-name span만 따로 봐도 dependency action은 root action보다 평균 ~15.2 step 늦게 commit된다. LLaDA가 dependency-looking action을 더 늦고 더 불확실하게 확정한다는 점을 보여준다.

단, 이것은 "gold dependency를 맞췄다"는 correctness 증거가 아니라, denoising 과정에서 dependency-looking syntax가 root action과 다르게 다뤄진다는 diagnostic signal이다. generated dependency edge 대부분은 endpoint action이 gold hop에 안정적으로 매칭되지 않거나 schema-invalid surface를 포함한다.

9. 결론

v1은 LLaDA가 BFCL function schema를 보고 action intent를 형식적으로 생성할 수 있음을 보여줬다. 하지만 세 가지 문제가 남았다. 첫째, under-generation: 50개 sample 중 44개에서 generated action이 gold hop보다 적었다. 둘째, state-dependent input hallucination: prior result가 필요한 값을 임의 concrete value로 채웠다. 셋째, dependency visibility 부족: natural-language [A] unit만으로는 어떤 action이 다른 action의 결과를 필요로 하는지 추적하기 어려웠다.

v2는 이 문제를 구조화된 numbered plan, deterministic state view, hybrid matcher로 다시 분석했다. 그 결과 state가 보이고 dependency syntax가 있어도 action recovery와 gold DAG recovery는 여전히 제한적이었다.

state-view rerun은 중요한 혼동을 줄였다. multi_turn_base_35처럼 user query만으로는 hidden path를 알기 어려운 case에서도, current state가 prompt에 들어간 상태로 모델을 평가할 수 있다. 그럼에도 action recovery는 제한적이었다. explicit $id 문법은 더 많은 dependency-looking structure를 만들었지만, gold DAG dependency와 안정적으로 맞지는 않았다. flat은 더 단순한 형식으로도 비슷한 action recall을 냈고, strict single-hop recall은 조금 더 높았다.

Confidence trace는 별도의 긍정 신호를 남겼다. v2에서 valid tool/schema-valid action은 invalid surface보다 높은 confidence를 보였고, explicit condition의 dependency action은 root action보다 낮은 confidence와 늦은 commit step을 보였다. 이는 DLM denoising 과정 안에 surface validity와 dependency-looking syntax에 대한 신호가 있음을 보여준다. 다만 covered action과 wrong action의 confidence 차이는 작고, generated dependency edge가 gold DAG와 안정적으로 align되지 않기 때문에 confidence를 correctness나 dependency recovery의 직접 증거로 해석할 수는 없다.

state가 보여도, dependency 문법이 있어도, recovery는 여전히 제한적이었다.

① 두 condition 모두 70개 turn 전체에서 parse 가능한 plan을 만들었다 (format_parse_rate=1.0).
② explicit은 더 많은 action, valid tool name, $id edge를 만들었다.
③ flat은 action 수·duplicate가 적고, strict single-hop hybrid recall은 약간 더 높았다.
④ hybrid matched gold-hop recall은 거의 같다: explicit 0.366 vs flat 0.359.
⑤ 두 condition 모두 gold dependency structure를 안정적으로 복구하지 못했다.
⑥ token confidence는 valid/invalid surface는 가르지만, correctness를 강하게 가르지는 못했다.
⑦ explicit의 $id dependency action은 root action보다 낮은 confidence + 늦은 commit step: trace-level signal 존재.
⑧ 그러나 그 signal이 gold DAG edge와 clean하게 align되지 않아 dependency recovery 증거로 보기 어렵다.

v2의 진단적 가치: 성공률 향상보다 실패 원인을 분해해서 보는 데 있다. state를 보여주는 것만으로 planning 문제가 해결되지는 않는다. dependency 문법을 주는 것만으로 dependency recovery가 생기지는 않는다. 하지만 이제 tool validity, schema validity, action recovery, dependency recovery, denoising signal을 분리해서 볼 수 있는 프레임이 갖춰졌다.
